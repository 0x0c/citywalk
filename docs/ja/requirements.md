# アプリ内メッセージ配信基盤の要件

このドキュメントは、citywalk のサーババックエンドが提供するアプリ内メッセージ配信機能の要件を
一覧にしたものです。要件には識別子を振ってあり、[`roadmap/`](../../roadmap/README-ja.md) の各設計
項目とテストケースの双方から参照します。設計の判断と根拠はロードマップ項目にあり、このドキュメント
は「何を満たすべきか」だけを扱います。

## 1. 目的とスコープ

### 1.1 目的

citywalk のモバイルアプリ（iOS と Android）の利用者に対して、アプリを使っている最中の画面上に、
文脈に応じたメッセージを表示します。プッシュ通知がアプリの外から利用者を呼び戻す手段であるのに
対して、アプリ内メッセージはすでにアプリを開いている利用者に、その瞬間の行動に応じて情報を届ける
手段です。設計の主眼は次の3点に置きます。

- **文脈性**：どの利用者かだけではなく、いま何をしているかで出し分けられること。
- **即時性**：表示の判定にネットワークの往復を挟まず、画面遷移を止めないこと。
- **統制**：施策が増えても、利用者1人あたりの表示回数と表示順序が破綻しないこと。

### 1.2 スコープ

| 区分 | 内容 |
|---|---|
| 対象 | メッセージ定義の管理、配信対象の解決、端末向け配信、トリガーと表示条件の定義と配布、表示頻度と優先度の統制、A/B テストとホールドアウト、多言語対応、効果測定イベントの収集と集計、レポート |
| 初期は対象外 | プッシュ通知、メール、SMS の送信、Web とデスクトップ向けの配信、位置情報を用いたジオフェンス、管理画面の実装 |
| 恒久的に対象外 | クライアント SDK そのものの実装。本ドキュメントは SDK に要求する責務だけを定めます |

将来のマルチチャネル化に備えて、メッセージの抽象をチャネルに依存しない施策定義と、チャネル固有の
コンテンツに分離します。ただし初期の実装で作るのはアプリ内メッセージのチャネルだけです。

### 1.3 前提

- バックエンドの言語は Go とします。
- 想定規模は月間アクティブ利用者数（Monthly Active Users、以下 MAU）で 100 万から 1000 万です。
- クライアントは iOS と Android のネイティブアプリで、オフライン状態での動作を要件に含みます。
- 本基盤は単独のシステムとして完結し、外部サービスのメッセージング機能に依存しません。

## 2. 用語

以降、次の用語を厳密にこの意味で使います。

- **チャネル**：アプリがインストールされた端末1台を指す識別単位です。SDK の初回起動時にサーバが
  識別子を発行します。配信と表示の最小単位です。
- **ユーザー**：citywalk のアカウントです。1人のユーザーが複数のチャネルを持つ場合があります。
  ログイン前は、ユーザーに紐づかないチャネルが存在します。
- **属性**：チャネルまたはユーザーに付随する型付きの値です。アプリのバージョン（文字列）、累計歩行
  距離（数値）、登録日時（時刻）などが該当します。
- **タグ**：真偽値としてのみ扱う軽量な属性です。内部的には属性の特殊形として実装します。
- **イベント**：端末で発生した出来事の記録です。起動、画面表示、アプリが定義するカスタムイベントの
  3系統があります。トリガーの評価と効果測定の双方で使います。
- **セグメント**：属性とイベント履歴に対する述語式で定義されるチャネルの集合です。
- **メッセージ**：施策の定義単位です。オーディエンス、トリガー、表示条件、コンテンツ、配信期間、
  統制ルールを1つにまとめます。
- **バリアント**：メッセージが持つコンテンツの実体です。A/B テストの各案と各言語版が該当します。
- **トリガー**：メッセージの表示を試みるきっかけとなる出来事の条件です。
- **表示条件**：トリガーが成立した後、実際に表示してよいかを判定する追加の条件です。
- **キャンセルトリガー**：待機中のメッセージを表示前に取り消すイベント条件です。
- **配信ペイロード**：サーバがチャネルへ配布する、その端末で評価対象となるメッセージ定義の集合です。
- **表示**：メッセージが実際に画面へ描画されたことを指します。
- **結末**：表示されたメッセージがどう閉じられたかを指します。ボタン押下、閉じる操作、自動クローズ、
  割り込みの4種類があります。
- **ホールドアウト**：効果測定のために、対象でありながら意図的にメッセージを表示しない集団です。

## 3. ドメインモデル

```
プロジェクト
  └── チャネル ──(n:1)── ユーザー
        │                   │
        │                   └── 属性 / タグ
        └── イベント（時系列）

プロジェクト
  ├── セグメント ── 述語式（属性とイベント集計を参照）
  └── メッセージ
        ├── オーディエンス      … セグメント参照とインラインの述語式
        ├── トリガー[]          … 表示を試みるきっかけ
        ├── 表示条件[]          … 表示可否の追加条件
        ├── キャンセルトリガー[] … 表示前の取り消し条件
        ├── スケジュール        … 有効期間、時間帯、タイムゾーン
        ├── 統制ポリシー        … 優先度、頻度上限、ホールドアウト
        └── バリアント[]        … コンテンツ（A/B 案 × 言語）
```

**オーディエンス**と**トリガー**の区別が、このモデルで最も重要な点です。オーディエンスは、その
利用者が対象母集団に含まれるかという条件で、変化はゆるやかであり、サーバで解決できます。トリガー
と表示条件は、いまこの瞬間に表示してよいかという条件で、秒単位で変化し、端末でしか判定できません。
2つを混同するとアーキテクチャが破綻するため、データモデルの段階で分離します。

## 4. 機能要件

要件の識別子は `FR-<領域>-<連番>` の形式とし、テストケースと1対1で対応させます。

### 4.1 メッセージ定義（FR-MSG）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-MSG-01 | メッセージを作成、参照、更新、削除できること。状態は下書き、予約済み、配信中、一時停止、終了、アーカイブを持ち、遷移は前進のみとする | Must |
| FR-MSG-02 | 表示形式として、中央ダイアログ、画面端のバナー、全画面、任意の HTML コンテンツをサポートすること | Must |
| FR-MSG-03 | 各形式のコンテンツで、見出し、本文、画像、ボタン（最大2）、閉じるボタンの有無、配色、角丸、表示位置、自動クローズまでの秒数を指定できること | Must |
| FR-MSG-04 | ボタンにアクションを紐づけられること。アクションは、閉じる、外部リンクを開く、アプリ内画面への遷移、カスタムイベントの発火、属性の更新を複合して指定できる | Must |
| FR-MSG-05 | コンテンツ定義がスキーマバージョンを持ち、SDK が未知のバージョンを受け取ったときは、そのメッセージを安全に無視できること | Must |
| FR-MSG-06 | 複数の画面を順に見せる体験（アンケート、オンボーディングなど）を定義でき、利用者の入力を回答イベントとして収集できること | Should |
| FR-MSG-07 | メッセージを複製できること。複製は下書き状態で作られ、配信実績を引き継がない | Should |
| FR-MSG-08 | 施策定義とチャネル固有のコンテンツをデータモデル上で分離し、将来のマルチチャネル化に備えること | Should |

### 4.2 オーディエンスとセグメント（FR-AUD）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-AUD-01 | オーディエンスを述語式で定義できること。参照できるのは、チャネル属性（プラットフォーム、アプリバージョン、SDK バージョン、ロケール、タイムゾーン、通知の許諾状態、初回起動日時、最終起動日時）、ユーザー属性、タグ、イベントの集計値 | Must |
| FR-AUD-02 | 述語式が、論理演算のネスト、比較演算、集合演算、文字列演算、意味的バージョン比較、相対時刻の指定をサポートすること | Must |
| FR-AUD-03 | イベントの集計を条件に使えること。直近 N 日間にイベントが M 回以上または未満、およびイベントを一度も発生させていないこと | Must |
| FR-AUD-04 | 述語式を再利用可能なセグメントとして保存し、複数のメッセージから参照できること。セグメントの更新は参照元すべてに反映される | Must |
| FR-AUD-05 | 新規利用者のみ、通知を許諾していない利用者のみといった頻出条件をプリセットとして提供すること | Should |
| FR-AUD-06 | セグメントの推定到達人数を管理 API から取得できること。全数の計算が重いときは標本推定でよいが、推定であることと誤差の範囲を返すこと | Should |
| FR-AUD-07 | テストデバイスを指定し、下書き状態のメッセージを実機で確認できること。テストデバイスへの配信は、頻度上限とホールドアウトを迂回する | Must |
| FR-AUD-08 | セグメントの更新モードとして、定期的な再計算と、属性変更の即時反映を選択できること | Should |

### 4.3 トリガーと表示条件（FR-TRG）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-TRG-01 | トリガー種別として、起動とフォアグラウンド復帰、カスタムイベント、特定画面の表示、アプリ更新後の初回起動、累計利用時間の到達、初回起動をサポートすること | Must |
| FR-TRG-02 | トリガーに発生回数を指定できること | Must |
| FR-TRG-03 | トリガーにイベントプロパティの条件を付与できること | Must |
| FR-TRG-04 | 複数のトリガーを論理和で結合でき、いずれか1つの成立で表示候補になること | Must |
| FR-TRG-05 | キャンセルトリガーを定義でき、待機中のメッセージが指定イベントの発生によって取り消されること | Should |
| FR-TRG-06 | 表示条件として、トリガー成立から表示までの遅延を指定できること | Must |
| FR-TRG-07 | 表示条件として、特定の画面でのみ表示する、または特定の画面では表示しないという制限を指定できること | Must |
| FR-TRG-08 | 表示条件として、ネットワークの接続状態を指定できること | Could |
| FR-TRG-09 | トリガー成立時に表示できなかった候補を、破棄するか次の機会まで保持するかを選択できること。既定は破棄とする | Should |

### 4.4 スケジュールと配信統制（FR-CTL）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-CTL-01 | メッセージに有効期間を設定でき、終了日時を過ぎたメッセージが端末側でも表示されないこと | Must |
| FR-CTL-02 | 有効期間を端末のローカルタイムゾーン基準で指定できること | Should |
| FR-CTL-03 | 曜日と時間帯による表示可能時間の制限を設定できること | Could |
| FR-CTL-04 | メッセージごとに優先度を設定でき、同時に複数が表示可能になったときは優先度が最も高い1件だけを表示すること | Must |
| FR-CTL-05 | 同一メッセージの表示上限として、通算の表示回数と、表示間隔の最小値を設定できること | Must |
| FR-CTL-06 | プロジェクト全体の表示上限を設定でき、上限に達したときは優先度の低いメッセージから抑止されること | Must |
| FR-CTL-07 | プロジェクト全体の表示上限の対象外とする例外を指定できること | Should |
| FR-CTL-08 | 画面上に同時に表示されるメッセージが常に1件であること | Must |
| FR-CTL-09 | 利用者がメッセージを閉じた直後の一定時間は、次のメッセージを表示しないこと | Should |
| FR-CTL-10 | 特定のメッセージについて、表示の直前にサーバへ確認を行うモードを選択できること | Should |

### 4.5 実験と最適化（FR-EXP）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-EXP-01 | 1つのメッセージに複数のバリアントを定義し、指定した配分比率で A/B テストを実施できること | Must |
| FR-EXP-02 | バリアントの割当が、同一の利用者に対して常に同じ結果になること | Must |
| FR-EXP-03 | ホールドアウトを設定でき、非表示にした対象にも記録を残して効果の比較対象にできること | Must |
| FR-EXP-04 | プロジェクト全体のすべての施策から除外される恒久的な対照群を設定できること | Could |
| FR-EXP-05 | バリアントの配分比率を配信中に変更でき、変更後も既存の割当が原則として維持されること | Should |

### 4.6 多言語対応（FR-L10N）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-L10N-01 | バリアントに言語コードを紐づけ、端末のロケールに応じたコンテンツを配信できること | Must |
| FR-L10N-02 | 端末のロケールに一致する言語版がないときは、言語のみの一致、次いで既定言語へフォールバックすること | Must |
| FR-L10N-03 | 言語ごとに画像を差し替えられること | Should |

### 4.7 配信 API（FR-API）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-API-01 | SDK が端末を登録および更新し、識別子と認証トークンを取得できること。属性、ロケール、タイムゾーン、アプリバージョン、通知の許諾状態を同時に送信できる | Must |
| FR-API-02 | SDK が、その端末で評価対象となるメッセージ定義の集合を一括で取得できること | Must |
| FR-API-03 | 配信ペイロードの取得が条件付きリクエストに対応し、変更がないときは本文を返さないこと | Must |
| FR-API-04 | 配信ペイロードに、次に同期すべきタイミングのヒントを含めること | Must |
| FR-API-05 | SDK がイベントをバッチで送信でき、オフライン中に蓄積されたイベントもまとめて送信できること | Must |
| FR-API-06 | イベントの送信が冪等であり、同一イベントの再送が二重に計上されないこと | Must |
| FR-API-07 | 配信ペイロードのサイズに上限を設け、超過時は優先度順に切り詰めること。切り詰めが起きた事実を観測できること | Should |
| FR-API-08 | 表示直前のサーバ確認のための軽量な API を提供すること。応答が得られないときは表示しない | Should |

### 4.8 効果測定とレポート（FR-RPT）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-RPT-01 | 表示、ボタン押下、閉じる操作、自動クローズ、統制による抑止、ホールドアウトによる非表示のイベントを収集すること | Must |
| FR-RPT-02 | メッセージ単位とバリアント単位で、表示数、表示した利用者の実数、クリック数、クリック率、閉じられた割合を集計できること | Must |
| FR-RPT-03 | 任意のカスタムイベントをコンバージョンとして指定し、表示後 N 時間以内の発生を計上できること | Must |
| FR-RPT-04 | バリアント間およびホールドアウトとの比較レポートを取得できること | Must |
| FR-RPT-05 | 抑止の理由の内訳を可視化できること。施策が想定どおり届いていない原因の切り分けに必要となる | Should |
| FR-RPT-06 | 日次と時間別の時系列でレポートを取得できること | Should |
| FR-RPT-07 | イベントの生ログを外部のデータ基盤へエクスポートできること | Could |

| FR-OPS-03 | 配信中のメッセージを即座に停止でき、停止の指示から端末へ反映されるまでの目標時間を定義すること | Must |
| FR-OPS-04 | メッセージのプレビューとテスト配信ができること | Should |

## 5. 非機能要件

### 5.1 性能（NFR-PERF）

| ID | 要件 |
|---|---|
| NFR-PERF-01 | 端末上の表示判定にネットワークの往復を伴わないこと。トリガーの成立から描画の開始までにサーバ通信を必要としない（サーバ確認モードを除く） |
| NFR-PERF-02 | 配信ペイロード取得 API の応答時間を、中央値 40 ミリ秒未満、99 パーセンタイル 200 ミリ秒未満とする。本文を返さない応答では 99 パーセンタイル 50 ミリ秒未満とする |
| NFR-PERF-03 | イベント収集 API の応答時間を 99 パーセンタイル 100 ミリ秒未満とする。受理だけを保証し、処理は非同期でよい |
| NFR-PERF-04 | ピーク時に、配信ペイロード取得を毎秒 1000 リクエスト、イベント受理を毎秒 1 万件、単一リージョンで処理できること |
| NFR-PERF-05 | アプリの起動時に、配信ペイロードの同期が起動処理を止めないこと。初回起動時のみ、一定時間だけ初回ペイロードの到着を待つ選択肢を提供する |

### 5.2 可用性と信頼性（NFR-REL）

| ID | 要件 |
|---|---|
| NFR-REL-01 | 配信ペイロード取得 API の可用性を月間 99.9 パーセント以上とする |
| NFR-REL-02 | 配信基盤の障害時も、端末にキャッシュ済みのペイロードでメッセージの表示が継続すること |
| NFR-REL-03 | イベントが受理後に永続化され、下流の処理が停止しても失われないこと |
| NFR-REL-04 | 端末がオフラインでもトリガーの評価と表示が動作し、イベントが端末に蓄積されて復帰時に送信されること。蓄積の上限を超えた分は古いものから破棄する |
| NFR-REL-05 | 配信停止の指示が、次回の同期時までに端末へ反映されること |

### 5.3 一貫性（NFR-CONS）

| ID | 要件 |
|---|---|
| NFR-CONS-01 | メッセージ定義の変更が、最終的に全端末へ反映されること。反映の目標時間は15分以内とする |
| NFR-CONS-02 | 表示頻度の上限を端末単位で厳密に守り、複数端末をまたぐ利用者単位では結果整合とする。厳密さが必要な施策はサーバ確認モードを使う |
| NFR-CONS-03 | 実験のバリアント割当が、同一の利用者と同一の実験に対して恒久的に安定であること |

### 5.4 セキュリティとプライバシー（NFR-SEC）

| ID | 要件 |
|---|---|
| NFR-SEC-01 | SDK との通信をすべて TLS 1.2 以上とする |
| NFR-SEC-02 | チャネルが自身に紐づくデータだけにアクセスできること。他のチャネルの識別子を指定しても操作できない |
| NFR-SEC-03 | 端末へ配布するペイロードが解析される前提で設計すること。機密性のあるオーディエンス条件は端末へ渡さず、サーバ側で解決した結果だけを配布する |
| NFR-SEC-04 | 管理 API に、標準的な認証基盤による認証と、役割にもとづく認可を必須とする |
| NFR-SEC-05 | 個人を直接に識別する情報を本基盤に保存しないこと。利用者の識別は不透明な識別子で行う |
| NFR-SEC-06 | 利用者からの削除要求に応じて、当該利用者のチャネル、属性、イベント履歴を削除できること |
| NFR-SEC-07 | イベント収集 API がレート制限を持ち、単一チャネルからの異常な送信量でシステム全体が劣化しないこと |
| NFR-SEC-08 | HTML 形式のコンテンツが、隔離された描画環境でのみ表示される前提とし、保存時に許可されないスキームを検証すること |

### 5.5 運用性（NFR-OBS）

| ID | 要件 |
|---|---|
| NFR-OBS-01 | 分散トレース、構造化ログ、メトリクスを標準的な規格で出力すること |
| NFR-OBS-02 | 施策ごとに、配布された数、表示された数、抑止された数とその理由を1分粒度で監視できること |
| NFR-OBS-03 | スキーマ変更を伴う配備が、稼働中の旧バージョンの SDK を壊さないこと |
| NFR-OBS-04 | 過去2世代の SDK のメジャーバージョンを同時にサポートすること |

## 6. クライアント SDK に要求する責務

本基盤の設計は、SDK が次を担うことを前提とします。サーバだけでは要件を満たせないため、境界を
明示します。

1. 配信ペイロードの取得、永続キャッシュ、差分の適用。
2. トリガー（イベントの発生回数、画面遷移、セッション時間）の状態管理と評価。
3. 表示条件の評価、遅延タイマーの管理、キャンセルトリガーによる取り消し。
4. メッセージごとの表示回数と最終表示時刻の永続化、および頻度上限の適用。
5. 表示候補が複数あるときの、優先度による選択。
6. 表示の直列化（同時に1件だけ）。
7. 各コンテンツ形式の描画とアクションの実行。
8. 効果測定イベントの生成、永続化、バッチ送信、再送。
9. サーバ時刻との差分を用いた、端末の時計の改ざんへの耐性。

## 7. 制約と未決事項

| # | 項目 | 現状の方針 |
|---|---|---|
| 1 | 配信ペイロードは端末上で解析できる | 機密性のある条件はサーバ側の解決に寄せます（NFR-SEC-03）。設計で緩和済みです |
| 2 | 端末の時計は信頼できない | サーバが発行する絶対時刻と端末の単調時計で期限を判定します。ずれが閾値を超える端末は検知して記録します |
| 3 | 複数端末をまたぐ厳密な頻度制御 | 原則は端末単位です（NFR-CONS-02）。厳密さが必要な施策はサーバ確認モードを使います |
| 4 | 位置情報を用いたトリガー | 初期のスコープ外です。街歩き用途で将来必要になる見込みが高いため、トリガー種別を拡張できる設計にします |
| 5 | 施策間の連鎖 | 初期のスコープ外です。表示イベントをトリガーに使えるため、簡単な連鎖は既存の機能で表現できます |
| 6 | 管理画面 | 本ドキュメントは API までを定めます。画面は API の確定後に別途設計します |
| 7 | 想定規模の確度 | MAU 100 万から 1000 万を前提に試算しています。実測に応じて構成を段階的に適用します |
