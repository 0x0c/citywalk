## はじめに

実験のバリアントとホールドアウトの割当を、保存ではなく計算で決めます。割当とは、安定した識別子と実験
ごとのソルトを合わせてハッシュし、1万個のバケットのどれかへ落とし、そのバケットを順序付きの範囲表で
引いた結果です。範囲表はバケットの範囲をバリアントへ対応づけ、1つの範囲をホールドアウトに予約します。
何も書き込みません。同じ識別子と同じ実験は、どのサーバでも、どの端末でも、いつでも同じバケットを返します。
データベースを復元した後も同じです。

割当は、サーバと端末が通信せずに一致しなければならない数少ない場所の1つです。サーバはペイロードを
組み立てながらバリアントを選び、レポートは数週間後に同じバリアントへ表示を帰属させなければなりません。
両側が持つ入力の純粋な関数にすることが、その一致を追加の仕組みなしに与える唯一の作り方です。

## 動機

素直な設計は割当を保存します。利用者が実験の対象に初めてなったとき、バリアントを乱数で引き、その組を表へ
書きます。理解しやすく、たいていの最初の実装が採る形で、そして最初は見えにくい費用を3つ積み上げます。

1つめは量です。忙しいプロジェクトが走らせる実験の数へ 1000 万人を掛けると、上限なく育ち、しかも
ペイロードの組み立てごとに読まれる表へ育ちます。ナノ秒で計算できた情報のため、基盤でもっとも頻度の高い
経路へ行の参照を1つ置く形です。2つめは脆さです。割当の表は、バックアップし、基盤の他の部分と
整合させて復元し、実験の定義が変わったら移行しなければならない状態になります。そして表を失った復元は、
全参加者を黙って引き直します。何も失敗せずに実験だけが無効になります。3つめは分裂です。端末はバリアントを
描画するために割当を知る必要があるため、サーバがペイロードごとに割当を送るか、両側が食い違うかの
どちらかになります。

表示のたびに引き直す方式がもう1つの素朴な選択肢で、こちらは単純に誤りです。実験は、2つの集団が経験した
ことの差を測ります。月曜に案 A、火曜に案 B を見た利用者はどちらの集団にも属さず、両方を汚染します。

割当を計算にすると、4つの問題が一度に消えます。残る仕事は、その計算を正しくすることです。一様であること、
実験のあいだで独立であること、配分比率の変更に対して安定であること、ログインで識別子が変わったときの
挙動が定義されていることの4つです。以下の設計は、この4つを扱います。

## 詳細設計

### ユニット1：識別子とログインの遷移

割当は、チャネルがアカウントに紐づいているときは利用者の識別子を、そうでないときはチャネルの識別子を
ハッシュします。利用者の識別子を優先することで、実験は同じ人の電話とタブレットで一貫します。これは端末
ごとの識別子では得られない性質です。

ログインは識別子を変え、したがって実験の途中で割当を変えうるものです。端末はこれを固定で扱います。
メッセージを一度表示したら、使ったバリアントを表示の記録と並べて残し、以後そのメッセージにはそれを
使い続けます。案 A を見た後でログインした利用者は、案 A を見続けます。分析は、再計算ではなく表示の記録から
バリアントを読みます。これで固定はレポートにとっても拠り所になります。

### ユニット2：バケットを決める関数

バケットは、実験のソルトと区切り文字と識別子を連結した 64 ビットのハッシュを、1万で割った余りです。1万
というバケット数は、配分の粒度を 0.01 パーセントに固定します。施策の担当者が書くどの配分よりも細かく、
範囲表を小さく保てる程度には粗いものです。

ソルトは実験ごとに生成し、再利用しません。ソルトがなければ、どの実験も同じ識別子を同じバケットへ落とす
ため、ある実験の案 A の集団は次の実験の案 A の集団とまったく同じになります。実験をまたいで露出が相関すると、
各実験の結果が他の実験の結果に依存します。共通のソルトが引き起こすのはこの失敗であり、後からの分析では
取り消せません。

ハッシュには、暗号学的でない高速な 64 ビット関数を使います。求めているのは一様性であって予測不能性では
ないからです。暗号学的ハッシュも一様性は満たしますが、ペイロードの組み立てごとにスループットの費用を
払います。そして追加で得られる性質、すなわち特定のバケットへ落ちる識別子を探索する攻撃者への耐性は、
ここでは何も守りません。citywalk 自身のダイアログのバリアントに自分を押し込んだ利用者は、何も得ない
からです。

### ユニット3：範囲表と配分比率の変更

各実験は、バケットの範囲をバリアントへ対応づける順序付きの表を持ちます。バケット 0 から 4,999 が案 A、
5,000 から 9,999 が案 B、といった形です。割当は、配分比率に対する計算ではなく、表の参照です。

配分比率から都度計算するのではなく範囲を保存することが、実験途中の比率変更を安全にします。計算による
配分は、どれか1つの比率が変わるとバケットを動かすため、50 対 50 を 60 対 40 へ動かすと、すでに測定中の
案から利用者が移動してしまいます。明示的な表があれば、比率の変更は、保てるバケットをすべて保ち、新しい
比率が要求するぶんだけを動かす新しい表を計算できます。変更は時刻とともに記録するため、変更をまたぐ比較から
影響を受けたバケットを除外できます。

### ユニット4：ホールドアウト

施策のホールドアウトは、同じ表のなかの予約された範囲です。5 パーセントのホールドアウトは 500 バケットを
予約し、そこへ落ちたチャネルは、あらゆる意味でその施策の対象でありながら、コンテンツを受け取りません。

プロジェクト全体の対照群は、実験ごとではなくプロジェクトごとに固定したソルトを使います。そこに入った
利用者は、すべての施策から一貫して除外されます。2つの仕組みを分けておくことには意味があります。答える
問いが違うからです。片方は施策をその不在と比べ、もう片方は基盤をその不在と比べます。統合すると、ある
施策からの除外が、無関係なプロジェクト水準の決定に左右されてしまいます。

### ユニット5：反実仮想の記録

ホールドアウトに入ったチャネルは、対象になったが表示を見送ったという事実を、施策と理由を添えたイベント
として出します。このイベントがなければ、ホールドアウトはデータをまったく生みません。そしてホールド
アウトが存在する理由である比較、すなわちメッセージなしでこの利用者たちが何をしたかには、分母がなくなります。

同じ理屈が、表示に記録したバリアントにも当てはまります。レポートは表示に記録されたバリアントへ帰属させ、
再計算した結果へは決して帰属させません。後の比率変更が、過去の表示を案のあいだで移動させないためです。

### ユニット6：検証

2つの性質は、前提にせず自動で検査します。一様性の検査は、大きな合成識別子の集団に対してバケット関数を
走らせ、分布の偏りが閾値を超えたら落とします。これが、ソルトの連結が識別子の形式とたまたま相関して
しまう誤りを捕まえます。一致の検査は、共通の検証データに対してサーバの実装と端末の実装が同じバケットを
返すことを確かめます。これが、同じ計算の2つの独立した実装がやがて抱える食い違いを捕まえます。文字列の
符号化の違いや、負のハッシュに対する符号付きの剰余がその例です。

## 検討した代替案

- **割当の表を保存する**：量、脆さ、一致のために採りません。計算できる値のためにもっとも頻度の高い経路へ行の
  参照を置き、復元が黙って引き直しうる状態を抱え、しかも描画のために端末へ割当を送る必要が残ります。
- **表示のたびにバリアントを引き直す**：誤りであるため採りません。両方の案に触れた利用者はどちらの集団にも
  属さないため、実験が生むはずの測定は、単に雑音が増えるのではなく汚染されます。
- **すべての実験で1つのソルトを共有する**：採りません。実験をまたいで案の所属が相関し、結果が互いに依存
  します。その依存は、後からの分析では切り離せません。
- **固定のバケットではなくコンシステントハッシュの環を使う**：目的が合わないため採りません。環は入れ物の
  個数が変わったときの移動を最小化する仕組みで、それが必要なのはシャーディングです。実験が変えるのは、
  個数の決まったバリアントに対する比率であり、それは明示的な範囲表のほうが直接的かつ読みやすく扱えます。
- **順番に、または巡回で割り当てる**：採りません。共有のカウンタが要るため、この設計で取り除いた保存状態
  が戻ります。加えて割当は登録の順序と相関するため、ある案が体系的に他の案より古い利用者で構成されえます。

- [ ] ユニット1：識別子の選択と、ログインをまたいで残る表示時の固定。
      識別子の選択は実装・試験済みで、いまは配信経路で実際に動いています。
      `internal/delivery/payload.buildEntry` が、ペイロード組み立ての時点で言語グループごとに
      `assign.Assign` を呼び（バケットの配分は CW-0003 が検証済みのバリアント比率から導きます）、
      その結果の variant_id を実際の表示が持つようになりました。CW-0009 がそれを campaign_rollup へ
      集計し、internal/event/report.Variants が読み戻します。このスキーマにはまだユーザーアカウントの
      紐づけがないため、今日使われている識別子は常にチャネル識別子で、ユーザー識別子ではありません。
      設計が言う「ユーザー識別子を優先する」性質は、その紐づけができて初めて実際に得られるものであり、
      これは逸脱ではなく、明記された簡略化です。このリポジトリで恒久的に未実装のまま残るのは表示時の
      固定そのもの（クライアント SDK の挙動）だけです。
- [x] ユニット2：1万バケットに対する、ソルト付きのバケット関数。
- [x] ユニット3：明示的な範囲表と、動かすバケットを最小にする比率の変更。
- [x] ユニット4：予約範囲としての施策のホールドアウトと、プロジェクト全体の対照群。
      予約範囲の仕組みも、いまは配信経路で実際に動いています。メッセージの HoldoutFraction が、
      `payload.buildEntry` が組み立てる範囲表の中に実際の範囲を予約し、そこへ落ちたチャネルは、
      一度も対象にならなかったチャネルと同じようにペイロードから除外されます。InProjectHoldout
      （別立てのプロジェクト全体の対照群）を呼ぶ箇所はまだありません。このスキーマには、それが
      対象とすべきプロジェクトという実体がまだ存在しません。
- [x] ユニット5：ホールドアウト該当のイベントと、記録されたバリアントにもとづくレポート。
      記録されたバリアントにもとづくレポートはできています（ユニット1の注記のとおり）。ホールドアウト
      該当のイベントも、いまは同じ配信経路で実際に動いています。`internal/delivery/payload.buildEntry`
      は、チャネルがメッセージのホールドアウトへ落ちると `recordHoldoutQualified` を呼びます。
      `recordHoldoutQualified` は `internal/event/ingest.Record` を通じて
      `model.KindHoldoutQualified` イベントを書き込みます。CW-0007 の `project_budget` 抑止のために
      `checkProjectBudget`（`internal/platform/connectserver/delivery.go`）が使っているのと同じ、
      サーバが副作用としてイベントを出す仕組みです。書き込みが失敗したときは握りつぶさず、呼び出し元へ
      返します。`internal/event/attribution` は、`model.KindHoldoutQualified` イベントを
      `HoldoutVariantID` の対象露出として既に読みます。
      `TestHoldoutQualifiedEventFromBuildIsCountedByAttribution`
      （`internal/delivery/payload/payload_integration_test.go`）は、実際の Postgres と Redis に対する
      試験です。`payload.Build` がチャネルを除外してイベントを残し、そのあとのコンバージョンが
      ホールドアウトへ帰属することを確かめます。InProjectHoldout によるプロジェクト全体のホールドアウトは、
      ユニット4の注記のとおり、変わらずまったく結線されていません。このスキーマには、それが対象とすべき
      プロジェクトという実体がまだ存在せず、それを追加することは本ユニットより大きな、別の変更です。
- [x] ユニット6：一様性の自動検査と、サーバと端末の一致の自動検査。
      一様性の検査と、一致を確認するための固定値表はどちらも実装済みです。この固定値表は、この
      リポジトリに端末側の実装が存在しないため、将来端末側の実装ができたときにそれを照合する
      サーバ側の成果物にあたります。
