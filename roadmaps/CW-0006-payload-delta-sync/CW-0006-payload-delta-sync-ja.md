## はじめに

端末が配信ペイロードを最新に保つためのプロトコルを定めます。構成要素は4つです。

- ペイロードの内容から導くエンティティタグ。
- タグが一致するときに本文を返さない条件付きリクエスト。
- ペイロードは大きいのに変更が小さい場合のための、カーソル方式の差分。
- 数千台の端末がペイロード組み立ての重い半分を共有できる、2段構えのキャッシュ。

同期の間隔はサーバが指定してジッタを加え、端末は誤りの際に全域ジッタ付きの指数バックオフで待ちます。

このプロトコルの目標は、よくある場合の費用をほぼゼロにすることです。ほとんどの同期は何も変わって
いないときに起きます。したがって最適化する価値があるのは「何も変わっていない」と答える経路であり、
本項目の他のすべての方式は、その経路を短く保つために存在します。

## 動機

citywalk が想定する規模では、基盤は1日およそ 600 万回の同期を受けます。そしてその圧倒的多数は、端末が
すでに持っているものと同一のペイロードに行き着きます。施策の定義が変わるのは1日に数回で、端末の同期は
1台あたり1日に数回です。この比率がプロトコルの形を決めます。興味深い問いは、ペイロードをいかに効率よく
転送するかではなく、いかに転送せずに済ませるかです。

毎回ペイロード全体を送る方式は最初の実装が採るもので、ペイロードが小さいために費用を見誤りやすいもの
です。50 キロバイトのペイロードを 600 万回送れば、1日 300 ギガバイトの下り通信が何も伝えずに流れます。
端末の側から見れば、それは求めていない利用者が払うモバイルデータです。街歩きのアプリを使うのは、屋外に
いて、携帯回線を使い、そこに気付く利用者です。

問題のもう半分は組み立ての費用で、条件付きリクエストだけでは解けない半分です。「このチャネルに変化は
あったか」に答えるには、結局そのチャネルがどのメッセージの対象かを知る必要があり、それはセグメントの
所属を読み、残りの述語式を評価することを意味します。それをリクエストごとに1日 600 万回行うと、同じ
セグメント、ロケール、アプリバージョンを持つ端末どうしで完全に同じ計算を繰り返します。そしてそれらの
組み合わせの種類は、端末の台数よりはるかに少ないものです。

## 詳細設計

### ユニット1：ペイロードの同一性

サーバは、チャネルのペイロードに対するエンティティタグを、端末が描画する内容を決める要素の並びを
ソートしてハッシュすることで計算します。要素は、対象となる各メッセージの識別子とバージョン、選ばれた
バリアントの識別子、統制ポリシーのバージョン、出力するスキーマのバージョンです。ハッシュには暗号学的
でない 64 ビットの関数を使います。タグが守るのは古さであって、偽造ではないからです。

タグを時刻ではなく内容から導くことが、同時編集のもとでの正しさを与えます。時刻にもとづくタグは、
無関係な施策が保存されただけで変わり、すべての端末に変わっていないペイロードを取り直させます。内容から
導いたタグは、描画結果が変わるときにちょうど変わります。したがって、あるチャネルに影響しない編集は、
そのチャネルに何の費用も課しません。

### ユニット2：条件付きリクエスト

端末は同期のたびに、保存しているタグを送ります。タグが一致したとき、サーバは変化がないことを示す状態を
本文なしで返します。この応答に対する要件上の予算は 99 パーセンタイルで 50 ミリ秒であり、本文を伴う
応答の 200 ミリ秒と対になります。

この予算を守るには、変化がない経路で完全な組み立てを行うわけにはいきません。そこでサーバは、計算した
タグをチャネルごとに短い有効期限付きでキャッシュします。有効期限のうちに来た再同期は、1回の参照と比較で
済みます。キャッシュを外したときは組み立てへ落ち、タグと本文の両方を計算して、比較の結果に応じた
ほうを返します。

### ユニット3：差分の方式

ペイロードが大きく、変わったのがその一部だけのとき、全体を送ると転送の大半が無駄になります。そこで端末は、
最後に適用したバージョンのカーソルを送ることができ、サーバはそのカーソル以降に追加または変更された要素と、
削除された要素の墓標を返します。

差分のプロトコルには、サーバがもう応えられないカーソルに対する答えを明示する必要があります。明示しないと、
端末とサーバは黙って食い違っていきます。サーバは上限付きの変更ログを保持し、ログより古いカーソルや
認識できないカーソルに対しては、エラーではなく完全なペイロードと新しいカーソルを返します。正しさへ
落ちる道が常にある点こそが、差分の経路を2つめの拠り所ではなく最適化にとどめます。

差分の方式は既定では無効です。転送量が問題にならない大きさのペイロードでは、プロトコルの複雑さの費用が
節約するバイト数を上回ります。そこでサーバは、実測したペイロードの大きさが見合った時点で、プロジェクト
ごとにこの方式を有効にします。

### ユニット4：2段構えの組み立てキャッシュ

ペイロードの組み立ては、端末をまたいで共有できる部分と、1台に固有の部分に分かれます。共有できる部分、
すなわちどのメッセージが対象でそのコンテンツが何かは、チャネルのセグメント所属、ロケール、
プラットフォーム、アプリのバージョン、対応スキーマのバージョンだけで決まります。固有の部分は、実験と
ホールドアウトの割当、そしてサーバ側の統制の状態です。

そこでサーバは、共有される入力をキーとする**バンドル**をキャッシュします。セグメントの所属は
[CW-0005](../CW-0005-segment-membership-index/CW-0005-segment-membership-index-ja.md) のチャネルごとの
所属ビットマップのハッシュで表し、キャッシュに当たった結果の上へチャネル固有の差し替えを適用します。
これらの入力が取りうる値の種類はチャネル数よりはるかに少ないため、1つのバンドルが多数の端末に応え、
組み立ての費用はリクエストごとから組み合わせごとへ下がります。

バンドルは時間ではなく施策の編集で無効化します。したがって変更は、キャッシュの期限切れを待たずに端末の
次の同期で届きます。無効化は施策をキーとするため、編集はその施策を含むバンドルだけを落とします。

### ユニット5：スケジュールとバックオフ

各応答は、端末が次に同期してよいもっとも早い時刻を含みます。サーバは基準の間隔を計算し、その一部の範囲へ
散らしたランダムなずれを加えます。リリース時にそろって同期した100万台が、15分後にまたそろって戻って
こないようにするためです。端末は、指定された時刻を過ぎた後のフォアグラウンド復帰でも同期します。これが、
長い間隔のあとに始まったセッションへ最新の施策を見せます。

誤りやタイムアウトのとき、端末は全域ジッタ付きの指数バックオフで待ちます。待ち時間は現在の上限そのもの
ではなく、ゼロから上限までの一様乱数から選びます。上限で再試行すると、同時に失敗したすべての端末の
再試行がそろってしまいます。それこそ、部分的な障害のあいだにバックオフが崩そうとしている殺到です。

### ユニット6：サイズと圧縮

応答は圧縮し、ペイロードのサイズ上限は圧縮後で測ります。対象集合が上限を超えたとき、配信サービスは
優先度の低いものから要素を落とし、対象の端末群と落とした件数を示すメトリクスを出します。

ここではメトリクスも切り詰めと同じくらい成果物です。切り詰められたペイロードは、誰も対象にならなかった
ペイロードとまったく同じに振る舞います。したがってメトリクスがなければ、静かに上限を超えて育った
プロジェクトは、施策の成績が悪いプロジェクトに見えます。

## 検討した代替案

- **同期のたびにペイロード全体を送る**：通信量と組み立ての費用のために採りません。圧倒的多数の場合に
  転送は何も伝えず、しかも屋外にいる利用者の携帯回線を消費します。街歩きのアプリが使われるのはまさに
  その場所です。
- **ポーリングではなくサイレントプッシュ通知でキャッシュを無効化する**：主たる仕組みとしては採りません。
  理由は
  [CW-0002](../CW-0002-hybrid-delivery-model/CW-0002-hybrid-delivery-model-ja.md) が述べたとおりで、
  サイレント配信は両プラットフォームで絞られ、信頼性が低いため、それに鮮度を預けると断続的に失敗します。
  ポーリングの上に加速手段として後から足す価値はあります。
- **1つのペイロードではなくメッセージごとにエンドポイントを分ける**：採りません。対象の施策ごとに
  取得すると、リクエスト数が施策の本数に比例します。基盤がうまくいくほど悪化する方向です。加えて、端末側の
  優先度の解決を定義可能にしている、一貫した1つのスナップショットを失います。
- **利用者ごとのペイロードをコンテンツ配信網から配る**：この規模では採りません。ペイロードはチャネル
  ごとに異なるため、エッジでのキャッシュは端末ごとに1エントリとなり、命中率は有効期限のうちに端末が
  2回同期する頻度で頭打ちになります。2段構えのバンドルキャッシュは、エッジが持ち込む無効化の問題なしに
  同じ効果をオリジンで得ます。
- **エンティティタグに暗号学的ハッシュを使う**：不要であるため採りません。タグが検出するのは、認証された
  通信路ですでに信頼しあっているサーバと端末のあいだの古さです。攻撃者に対する衝突耐性は何も生まず、
  基盤でもっとも頻度の高い経路でスループットを削ります。

- [x] ユニット2：チャネルごとのタグキャッシュが応える、条件付きリクエストの変化なし経路。
- [x] ユニット3：墓標と上限付き変更ログを備え、完全なペイロードへ落ちられるカーソル方式の差分。
      `internal/delivery/changelog` が上限付き変更ログです（`migrations/0013_delivery_change_log.sql`）。
      保持期間は7日で、この段階にはまだ持たないスケジューラの代わりに、書き込みのたびに機会的に
      刈り込みます（理由は `changelog.Retention` 自身のコメントに書いてあります）。
      `internal/delivery/cursor` が不透明なトークンで、変更ログの通し番号、チャネルのセグメント
      所属ビットマップのハッシュ（本ユニットのために追加し、ユニット4でも再利用する
      `internal/membership/reverse.Hash`）、発行時刻の3つからなります。`internal/delivery/deliver`
      の `computeDelta` がこの3つを組み合わせます。ハッシュの不一致、ログがもう覆っていない通し
      番号、復号できないカーソルのいずれであっても、エラーではなく完全なペイロードと新しいカーソル
      へ落ちます。このチェック欄の以前の注記が挙げていたチャネルごとの対象資格の問題(チャネルが
      セグメントに入る、出る)は、この所属ハッシュが解決します。そうした変化はすべてハッシュの
      不一致として捉えられるため、変更ログ自体はメッセージ単位の事象だけを追えばよくなります。
      そして今のところ存在するメッセージ単位の事象は
      `internal/platform/connectserver/admin.go` の `UpdateMessageState` だけです
      （`CreateMessage` は常に下書きで作成し、対象になることがないため、記録は要りません）。
      メッセージの配信ウィンドウが開くことにも変更ログへの書き込みは要りません。カーソル自身の
      発行時刻とメッセージの `window_start` を比べれば捉えられるからです。ウィンドウが閉じることに
      墓標はまったく要りません。`payload.Entry.ExpiresAt` がすでに CW-0002 の自己失効の契約を
      運んでいるからです。差分方式は `deliver.Config.DeltaModeEnabled` で切り替え、既定では無効です。
      プロジェクトという実体がまだ存在しないため、本物のプロジェクトごとの切り替えの代わりに、この
      段階限りの代替として使います。CW-0007 の `ProjectBudgetCap` がすでに同じ欠落を同じやり方で
      扱っています。テストは `internal/delivery/changelog/changelog_integration_test.go`（通し番号の
      単調増加、`Since` クエリ、刈り込み)、`internal/delivery/cursor/cursor_test.go`（符号化と復号の
      往復、でたらめな入力がエラーにならないこと)、`internal/delivery/deliver/deliver_integration_test.go`
      （新しいカーソルなら変わった分だけ届くこと、削除されたメッセージに墓標が付くこと、でたらめな
      カーソルや古すぎるカーソルが完全なペイロードへ落ちること、差分方式が無効ならカーソルを
      一切出さないこと）、そして `internal/platform/connectserver/admin_integration_test.go` の
      `TestUpdateMessageStateRPCRecordsTheChangeLog`（孤立したロジックだけでなく、実際の
      `UpdateMessageState` の配線を証明する）にあります。
- [ ] ユニット4：共有バンドルとチャネル固有の差し替えからなる、2段構えの組み立てキャッシュ。
      未実装です。ただし、これを見送っていた前提は変わりました。CW-0008 の実験とホールドアウトの
      割当は、いまはペイロードの組み立てに配線されており、共有バンドルの上に載せるべき本物の
      チャネル固有部分(どのバリアントか、あるいはホールドアウトかどうか)が実在します。それでも
      この回ではキャッシュの分割そのものは作りません。これは、測定された費用の問題がまだない経路への
      性能最適化であり、その根拠より先に作ることは、実装のガードレールがまさに禁じる抽象化に
      あたるからです。ただし見送る理由は、今は「分割する対象が何もない」ではなく「測定された必要が
      まだない」に変わっています。
- [x] ユニット5：サーバが指定するジッタ付きの間隔と、全域ジッタ付きの指数バックオフ。
      間隔とジッタは CW-0002 ユニット3の `internal/delivery/sync` パッケージであり、ここでも
      そのまま再利用し、変化なしの経路を含むすべての Sync 応答で返します。バックオフは端末側の
      挙動であり、CW-0002 ユニット5と同じ理由でこのリポジトリの対象外です。
- [x] ユニット6：圧縮、圧縮後のサイズ上限、切り詰めのメトリクス。
      圧縮はすでに使っている Connect プロトコルに組み込まれています。Connect のハンドラは既定で
      gzip に対応し、リクエストのヘッダーから交渉するため、追加のコードは要りません。サイズ上限と
      切り詰めのメトリクスは CW-0002 ユニット2のものです。今回、言語でラベル付けし、メトリクスが
      単なる件数だけでなくコホートも名指しするようにしました。
