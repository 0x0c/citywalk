## はじめに

オーディエンスの条件は、Common Expression Language（以下 CEL）で評価します。CEL は小さく、チューリング
完全ではない式の言語で、Go の実装があります。評価の対象は、型付きの属性レジストリです。述語式は式として
書かれ、保存時にレジストリに対して型検査を受け、ソース文字列ではなく構文木として保存されます。保存された
1本の構文木が2つの評価器を動かします。ペイロードの組み立て中に「このチャネルは対象か」を答える行単位の
評価器と、同じ構文木を SQL へ変換してセグメントの所属を一括計算する集合単位の評価器です。適合性の
テストスイートが両方を同じ検証データで動かし、結果が食い違ったら落とします。

2つの評価器があることが、これをライブラリの選択ではなく設計の項目にしています。オーディエンスに対する
問いは、規模が6桁違う2つの形で届きます。いま1チャネルか、一晩で1000万チャネルかです。片方だけを扱う
エンジンは、もう片方を手書きの2つめの実装へ押し出し、2つは食い違っていきます。

## 動機

オーディエンスの述語式は、施策の担当者の入力がそのままサーバの実行対象になる唯一の場所です。したがって
その設計は、表現力の問題である前に安全性の問題になります。述語式は人が管理画面で書き、保存され、
プロジェクトのすべてのチャネルに対して実行されます。その入力が停止しない繰り返しを書けるなら評価は
終わらず、担当者が触れてはならないデータへの参照を書けるなら、管理画面はデータ持ち出しの道具に
変わります。

すぐ思いつく2つの答えは、まさにこの点で破綻します。担当者に SQL を書かせる方式は表現力が最大ですが、
データベース全体を渡すことになります。基盤が所有していないテーブルも含めてです。文の検査をどれだけ
重ねても安全にはなりません。検査は毎回正しくなければならず、攻撃者は一度当たれば足りるからです。汎用の
スクリプト言語を書かせる方式は、同じ問題に停止性の問題が加わります。繰り返しを含む述語式は永久に走り、
永久に走るペイロードの組み立ては障害です。

3つめの答え、自前の述語式インタプリタは安全で、放っておけばこの設計が落ち着く先です。破綻するのは
正しさではなく費用です。実用になる述語式の言語には、構文解析器、型検査、比較と集合と文字列の演算子、
意味的バージョンの順序、相対時刻、空値の扱い、そして技術者ではない担当者に読めるエラーメッセージが
要ります。そしてそのすべてを、SQL への変換側でもう一度書くことになります。CEL は前半を、仕様と試験を
備え、評価が必ず停止することを保証された言語として提供します。したがって本項目に残るのは、citywalk に
固有の部分だけです。属性レジストリ、SQL への変換、イベントの集計がそれにあたります。

## 詳細設計

### ユニット1：属性レジストリ

述語式が参照できる名前は、すべてレジストリに宣言します。識別子、型（文字列、数値、真偽値、時刻、
意味的バージョン、文字列の集合）、出所（チャネルの項目、ユーザー属性、タグ、イベントの集計）、そして
機密かどうかを持ちます。レジストリはデータであるため、属性の追加はリリースではなく設定の変更です。

レジストリは3つの役割を同時に果たします。まず述語式に型を与えます。`app_version >= "2.10.0"` は
意味的バージョンとして比較され、文字列としては比較されません。文字列の比較では `2.9.0` が `2.10.0` より
大きくなってしまいます。次に到達できるデータを限定します。レジストリにない名前はコンパイルに失敗する
ため、レジストリが記述していないテーブルへはどの述語式も届きません。そして
[CW-0002](../CW-0002-hybrid-delivery-model/CW-0002-hybrid-delivery-model-ja.md) が必要とする機密の
印を持ちます。機密と印を付けた属性は、サーバが評価するオーディエンスの述語式には現れてよく、端末へ届く
トリガーの述語式には決して現れません。

### ユニット2：文字列ではなく木として保存する

保存された述語式は、構文木を JSON へ直列化した形で格納し、表示用に元のソース文字列を併せて持ちます。
実行されるのは木のほうで、ソースは説明のためのものです。

文字列ではなく木を保存することが、言語の変更に対して述語式の意味を安定させます。今日解析された式は、
構文解析器が更新されても意味を保ちます。解析はすでに終わっているからです。あわせて配信時の失敗が
1種類減ります。ペイロードの組み立てが構文エラーに出会うことはもうありません。解析できない述語式は保存の
時点で拒否されているからです。

### ユニット3：行単位の評価

ペイロードの組み立て中、サーバは候補となる各メッセージの述語式を、1チャネルの属性に対して評価します。
構文木は CEL の実行可能なプログラムへ一度だけコンパイルし、木の内容ハッシュをキーにキャッシュします。
コンパイルの費用はリクエストごとではなく述語式ごとに1回で済み、複数のメッセージが共有する述語式は1回
だけコンパイルされます。

評価は時間とデータの両面で上限を持ちます。CEL には停止しない繰り返しがないため、プログラムは自身の大きさに
比例した時間で終わります。属性の値は、呼び出し側が評価の前に用意する1つのマップから読むため、評価は
入出力を行わず、データベースが遅いという理由で遅くなることはありません。

### ユニット4：集合単位の評価

同じ構文木は、一括計算のための SQL の `WHERE` 句へも変換します。一括計算では、セグメントの所属をチャネル
表の全体に対して計算し直します。並行する SQL 表現を別に保守するのではなく、施策の担当者が実際に書いた木を
変換することが、2つの経路の一致を保ちます。述語式は1つで、その実行系が2つある、という構造にします。

とはいえ、1つの言語に2つの実行系がある構成は、微妙な食い違いが潜む場所です。そこで適合性のテスト
スイートを、テストの細部ではなく成果物としてこの項目に含めます。スイートは、検証用の集団に対して
述語式の集合を両方の実行系で評価し、1件でも食い違えば落とします。これが、既定の挙動が分かれる箇所を
捕まえます。空値と欠損値の扱い、文字列の照合順序、時刻の境界を含むかどうかがそれにあたります。

SQL へ変換できない構文は、保存時にその構文を名指しして拒否します。受理してから夜間バッチで失敗させる
形にはしません。

### ユニット5：イベントの集計

「直近7日でルート画面を3回以上開いた」のような条件は、配信時に生のイベントを走査して答えるわけには
いきません。1000万チャネルでは、走査だけで応答時間の予算を超えます。そこでエンジンは、事前に集計した
カウンタを読みます。収集の時点でロールアップを行い、チャネルごと、イベント名ごと、日ごとの回数を保持し、
期間付きの条件はその期間を覆うバケットを合計します。

日単位のバケットは、相対時刻の条件の粒度を1日に固定します。これは見落としではなく意図した取引です。
バケットを細かくすると、ロールアップの容量が比率のぶんだけ増えます。そしてオーディエンスの条件は、
端末が正確なローカル状態で評価するトリガーとは違い、時間単位の精度を必要としません。レジストリは集計
ごとの粒度を記録するため、ロールアップが持たない精度を求める条件は型検査で拒否できます。

### ユニット6：到達人数の推定

管理画面は、述語式に何チャネルが一致するかを示します。正確な数を出すには集合単位の評価が要りますが、
施策の担当者が試行錯誤する対話的な流れには遅すぎます。そこで管理画面は、チャネルの一様標本に対して評価
して比率を掛け、推定値を信頼区間と標本の大きさとともに返します。

区間を返すことは飾りではなく要件です。「およそ 40,000」と読む担当者と、「40,000、上下 12,000 の幅」と
読む担当者は違う判断をします。そして標本が小さいときに誠実なのは後者です。

## 検討した代替案

- **担当者に SQL を書かせる**：安全性のために採りません。データベースへ届く述語式は、そのなかの
  すべてのテーブルへ届きます。文の検査はあらゆる入力に対して正しくなければならず、攻撃者は隙間が1つ
  あれば足ります。表現力は確かに高いものの、citywalk が必要とするオーディエンス条件にそこまでの
  表現力は要りません。
- **汎用の組み込みスクリプト言語**：停止性と隔離のために採りません。繰り返しを含む述語式は永久に走り、
  戻らないペイロードの組み立ては障害です。加えて、完全な言語を隔離する作業は、危険な構文を最初から
  持たない言語を採用するよりはるかに広い範囲を正しく作ることを求めます。
- **自前の述語式インタプリタ**：安全性ではなく費用のために採りません。これは安全な設計であり、CEL は
  その既製の実例です。自前で書くとは、構文解析器、型検査、演算子の一式、技術者以外に読めるエラーを
  書き、要求が増えるあいだその言語を保守し続けることです。作業の中身は CEL のものと変わらず、しかも
  試験のない状態から始まります。
- **JSONLogic のような JSON 形式のルール表現**：記述と型付けのために採りません。入れ子の JSON で
  表したルールは差分として人が読みにくく、形式自体が型システムを持ちません。レジストリを動機づける
  意味的バージョンの比較は、検査の裏付けがないカスタム演算子として後付けすることになります。
- **CEL ではなく `expr-lang/expr` を使う**：僅差であり、評価の費用が支配的になったときは再検討する
  価値があります。速く、構文も親しみやすいものです。ここで CEL を採るのは、仕様があることと型検査が
  あることによります。型検査はユニット1 が最も強く依存する部分です。加えて、SQL への変換を単一の実装の
  挙動ではなく標準に対して検証できます。
