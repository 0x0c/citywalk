## はじめに

アプリ内メッセージ配信基盤を動かすランタイムとストアを定めます。選定の基準は、いつか到達しうる規模では
なく、先に示す負荷の見積もりです。サービスは Go、永続的な記録は PostgreSQL、高頻度の参照とカウンタは
Redis、イベントの継ぎ目は Kafka 互換のログ、効果測定は ClickHouse とします。クリエイティブのアセットは、
コンテンツ配信網の背後のオブジェクトストレージへ置きます。導入は段階的に行い、最初の段階で何を使わないか
も本項目で述べます。

議論を支えるのは負荷の見積もりです。citywalk が想定する規模では、配信の経路は毎秒数百リクエストであり、
これは小さい数字です。そしてこの小ささが誘惑を生みます。数字が支持しない規模に備えて作り込み、少人数の
チームにとってスループットの価値に見合わない運用の面積を増やしてしまう、という誘惑です。

## 動機

負荷の見積もりなしに行う技術選定は、習慣による選定です。そして失敗する2つの方向は、どちらも同じくらい
高くつきます。作りが小さすぎる失敗は、遅く、大きな音を立てて現れます。手軽さで選んだストアが、誰も
予測していなかった成長曲線のもとで応えなくなり、移行は追い込まれた状況で起きます。作りが大きすぎる失敗は、
早く、静かに現れます。最初の施策が出る前に状態を持つ系が5つ揃い、以後どの障害でも、当番の担当者は
一度も調べたことのない系へ向き合うことになります。

以下の数字がこの2つを分けます。したがって数字は、どの構成要素よりも先に置きます。数字はまた、選定を
検証可能にします。異論のある読み手は、好みではなく前提を指せます。

見積もりが決めない箇所を1つ挙げます。イベントのパイプラインです。作り込みすぎに見えるため、名指しして
おく価値があります。毎秒 600 イベントでは、永続的なログはスループットの要求ではありません。それは分離の
要求であり、理由は
[CW-0009](../CW-0009-event-ingestion-analytics/CW-0009-event-ingestion-analytics-ja.md) が述べた、
締め切りの無関係な3つの読み手にあります。ログの採用は構造についての決定であり、見積もりは構造について
何も言いません。

## 詳細設計

### ユニット1：負荷の見積もり

以下の数字は、想定範囲の上限を前提に置いています。すなわち月間アクティブ利用者数 1000 万、そのうち
4分の1がある日に活動し、1人あたり 2.5 セッションという前提です。

| 量 | 見積もり | 導出 |
|---|---|---|
| 日次アクティブ利用者数 | 250 万 | 1000 万の 25 パーセント |
| 1日のセッション数 | 625 万 | アクティブ利用者あたり 2.5 |
| ペイロードの同期 | 1日 625 万回、平均で毎秒およそ 70、ピークでおよそ 430 | セッションあたり1回、ピーク係数6 |
| 変化なしの応答 | 同期のおよそ 95 パーセント | 施策の編集は1日に数回 |
| イベント | 1日 5000 万件、平均で毎秒およそ 600、ピークでおよそ 3,500 | セッションあたり8件 |
| 配信の下り通信量 | 1日およそ 13 ギガバイト | 本文を返すのは5パーセント、圧縮後 40 キロバイト |
| チャネルの行数 | 1000 万行 | インストール済みの端末ごとに1行 |
| イベントの容量 | 圧縮後で1日およそGB、13か月でおよそTB | 5000 万行、生でおよそ 400 バイト |
| 逆方向の所属索引 | およそGB | 1000 万チャネル、1件およそ 100 バイト |

配信層の形を決めるのは同期の数字です。毎秒数百リクエストで、そのうち20回に19回は本文を返さないという
負荷は、アプリケーションのインスタンス数台が余裕を持って捌けるものです。
[`docs/ja/requirements.md`](../../docs/ja/requirements.md) の毎秒 1000 リクエストという要件は、
ピークの見積もりに対しておよそ2倍の余裕を持ちます。

### ユニット2：言語とサービスの枠組み

サービスは Go で書きます。配信と収集の経路は並行性が高く、確保するメモリに敏感で、その大半をストアの
応答待ちに費やします。これは Go のスケジューラと標準ライブラリが想定している負荷です。運用上の性質も
ランタイムの性質と同じくらい重要で、単一の静的なバイナリは配備の問題を1種類まるごと取り除きます。加えて
起動が速いため、トラフィックの急増に対して水平方向の増設が素早く効きます。

サービスのインターフェースは Protocol Buffers で定義し、Connect で提供します。Connect は1つの定義から、
gRPC のプロトコルと、JSON を本文とする通常の HTTP の両方を話します。したがってモバイル SDK は通常の
HTTP リクエストを出します。端末に gRPC のランタイムは不要で、経路上のプロキシや調査の道具がそのまま
使えます。サービス間の内部呼び出しはバイナリのプロトコルを使います。1つのスキーマが両側を生成するため、
サーバから乖離していく手書きのクライアントがなくなります。

本項目で確定するライブラリは次のとおりです。データベース接続には `pgx` と `sqlc` を、インメモリストア
には `go-redis` を使います。ログ用は `franz-go`、列指向ストア用は `clickhouse-go` です。述語式は
`cel-go`、ビットマップは `roaring`、ジョブキューは `river`、可観測性は OpenTelemetry の Go
モジュールを使います。

### ユニット3：永続的な記録

PostgreSQL は、施策の定義、バリアント、トリガー、ポリシー、セグメント定義、チャネル、ユーザー、属性、
監査ログを保持します。データ量は数千万行で、書き込みの頻度は低いものです。選定を決める要件は、定義の
保存に対するトランザクションの整合性、配信サービスの絞り込み走査のための部分索引、そして
[CW-0003](../CW-0003-message-definition-schema/CW-0003-message-definition-schema-ja.md) が丸ごと
格納するコンテンツのオブジェクトのための文書型です。

スキーマの変更は、配備の手順で適用するバージョン付きの移行として扱います。規則として、移行とそれに
依存するコードを同時に出荷しません。あるリリースでカラムを追加して埋め、次のリリースでそれを読みます。
この規則が、どの時点でも切り戻しを可能にします。

### ユニット4：高頻度の参照とカウンタ

Redis は、配信の経路がリクエストごとに読むものと、表示のたびに統制が更新するものを保持します。
[CW-0005](../CW-0005-segment-membership-index/CW-0005-segment-membership-index-ja.md) の逆方向の
所属索引、
[CW-0006](../CW-0006-payload-delta-sync/CW-0006-payload-delta-sync-ja.md) のタグのキャッシュと
組み立てのバンドル、
[CW-0007](../CW-0007-display-governance/CW-0007-display-governance-ja.md) のスライディング
ウィンドウカウンタが該当します。

ここに置くものはすべて、導出できるか、期限で消えるものです。この性質が選定を安全にします。ストア全体を
失っても、費用は再構築と応答時間の一時的な悪化であって、データではありません。唯一の例外がカウンタで、
失われると利用者のプロジェクト全体の予算が戻ります。設計はこれを受け入れます。代わりの案は、快適さの
閾値を守るために、表示の経路へ永続的な書き込みを置くことだからです。

カウンタの更新にはサーバ側のスクリプトを使います。2つのアプリケーションインスタンスからの読み取りと
加算が、どちらも最後の1回分の空きを見ることのないようにするためです。

### ユニット5：イベントのログ

Kafka 互換のログが、収集から3つの読み手へイベントを運びます。この規模のチームには、Kafka 本体よりも
Redpanda を既定とします。バイナリが1つで、協調のための別サービスが要らず、Kafka の拡張上限が問題に
ならない量に対して運用の面積が明確に小さいためです。

見積もりは、毎秒 600 イベントでログを要求しません。それでも採用するのは意図的です。得られるのは継ぎ目
です。読み手を再生して集計を作り直せ、4つめの読み手を収集へ触れずに足せ、遅いレポートがイベントの受理を
遅くできなくなります。これらの性質を後から作ることは、端末が依存している収集の経路を書き直すことを
意味します。

### ユニット6：効果測定の格納

ClickHouse が生のイベントと集計を保持します。負荷は追記が中心で、時間の範囲といくつかの次元による集約で
問い合わされ、施策の担当者が更新するレポートのために対話的な応答時間を必要とします。加えて、イベント
識別子によるマージ時の重複除去が要ります。このエンジンは、それをアプリケーション側の処理ではなく機能
として提供します。

生のイベントの保持期間は13か月とします。施策を1年前の同じ時期と比べられるようにするためです。集計は
小さいため、期限を設けずに保持します。

### ユニット7：クリエイティブのアセット

画像と HTML コンテンツはオブジェクトストレージへ置き、コンテンツ配信網を通して配ります。ペイロードは、
内容から導いた URL を運びます。内容にもとづく URL はアセットを不変にし、いつまでもキャッシュできる
ものにします。そして画像の差し替えは、キャッシュの無効化ではなく新しい URL を生みます。これが重要なのは、
半分の端末にだけ届いた差し替え画像が、2つの異なるものを表示する施策になるからです。

ペイロード自体はエッジから配りません。理由は
[CW-0006](../CW-0006-payload-delta-sync/CW-0006-payload-delta-sync-ja.md) が述べたとおり、チャネル
ごとに内容が異なるからです。

### ユニット8：定期実行

背後で走る処理、すなわちセグメントの再計算、集計の保守、施策の開始と終了、突き合わせは、PostgreSQL を
土台とするジョブキューで動かします。これで、ジョブを、それを引き起こす定義の保存と同じトランザクションの
なかで登録できます。別の系にあるキューはこれを提供できません。そして防げる失敗は、定義は保存されたのに
開始のジョブは登録されなかった、という状態です。

タイムゾーン基準のスケジュールは、チャネルを15分刻みのずれの区画へ振り分けて扱います。96 区画で、
実際に使われているすべてのずれを覆えます。毎時45分のずれを持つものも含みます。現地時間 09:00 に予定した
施策は、チャネルごとではなく区画ごとに1つの開始処理を登録します。

### ユニット9：認証

端末は、基盤が署名した短命のトークンで認証します。トークンはチャネルの識別子を束縛し、SDK はより長命な
登録用の資格情報でこれを更新します。チャネルをトークンへ束縛することが、他のチャネルの識別子を名指しても
何も得られないという要件を満たします。リクエストに含まれる識別子は無視し、トークンのなかの識別子を使う
からです。

管理 API は、組織の認証基盤で認証し、役割で認可します。初期の役割は閲覧者、編集者、管理者の3つです。
すべての変更操作は、実行者、対象、変更内容を記した監査の記録を残します。

### ユニット10：可観測性

サービスは OpenTelemetry のトレース、メトリクス、構造化ログを出します。一般的なサービス水準の信号に
加えて、基盤に固有の4つのメトリクスを一級のものとして扱います。どれも、健全に見える系のなかでは他に
現れない失敗を検出するからです。4つとは次のものです。

- ペイロードの切り詰め回数（[CW-0006](../CW-0006-payload-delta-sync/CW-0006-payload-delta-sync-ja.md)）。
- 所属の突き合わせで食い違った件数（[CW-0005](../CW-0005-segment-membership-index/CW-0005-segment-membership-index-ja.md)）。
- 理由ごとの抑止件数（[CW-0007](../CW-0007-display-governance/CW-0007-display-governance-ja.md)）。
- 非対応のスキーマバージョンのために飛ばされたメッセージの件数（[CW-0003](../CW-0003-message-definition-schema/CW-0003-message-definition-schema-ja.md)）。

いずれの失敗も、想定より表示の少ない施策を生み、どこにもエラーを残しません。ダッシュボードにたまたま
出ているものに委ねず、ここで名指ししているのはそのためです。

### ユニット11：段階的な導入

上のスタックは到達点であって、最初の配備ではありません。第1段階では、定義、オーディエンス、配信の3つの
サービスを1つのプロセスとして、PostgreSQL と Redis の上で動かします。イベントは PostgreSQL へ直接
書き、定期実行のジョブで集計します。最初の施策には十分で、担当者1人で運用できる大きさです。

ログと ClickHouse は第2段階で入れます。イベントの量が増え、集計ジョブの実行時間が制約になった時点です。
[CW-0001](../CW-0001-in-app-message-platform-scope/CW-0001-in-app-message-platform-scope-ja.md) の
サービス分割は、プロセスがいくつであろうと第1段階からコードのなかで保ちます。境界がすでにあれば後から
サービスを分けるのは安く、なければ高くつくからです。

## 検討した代替案

- **Kotlin と Spring Boot、または TypeScript と Node**：どちらも十分に成立します。ここで Go を採るのは、
  配信と収集の経路で優れるからです。この2つは基盤の高頻度経路であり、ロジックではなく並行性で律速します。
  加えて単一の静的バイナリという運用の単純さも理由です。Kotlin が有利になるのは管理側で、そこは基盤の
  なかでもっとも小さく、性能への感度ももっとも低い部分です。
- **効果測定も含めてすべてを1つの PostgreSQL に置く**：到達点としては採らず、第1段階では採ります。
  ユニット11 で述べたとおりです。行指向の格納は、レポートが行う集約に対して列指向のエンジンよりはるかに
  多くのデータを走査します。加えてインスタンスの共有は、レポートの応答時間をイベントの受理に結び付けます。
  それは
  [CW-0009](../CW-0009-event-ingestion-analytics/CW-0009-event-ingestion-analytics-ja.md) が退けた
  結合です。
- **ClickHouse ではなくマネージドのデータウェアハウス**：対話的なレポートには採らず、外部への書き出しに
  ついては再検討の価値があります。数十秒の問い合わせ時間は、担当者が更新するダッシュボードには合いません。
  加えて問い合わせごとの課金は、埋め込みレポートの費用を見られた回数に比例させます。
- **Redpanda ではなく Kafka**：僅差です。Kafka のほうが周辺の生態系は大きく、運用の知見も広く共有されて
  います。ここで Redpanda を採るのは面積のためです。基盤が必要としているのは順序を保つ永続的なログであり、
  Kafka の可動部の多さを正当化する拡張の余地は必要としていません。
- **常駐するサービスではなくマネージドの関数実行基盤**：採りません。配信の経路は組み立てバンドルの
  プロセス内キャッシュに依存しており、リクエストごとに実行を捨てるモデルはそれを失います。基盤でもっとも
  頻度の高い経路で、キャッシュ命中がストアへの往復に変わります。
- **HTTP と JSON の経路を持たず gRPC だけにする**：モバイル側の事情から採りません。SDK に gRPC の
  ランタイムが必要になり、モバイルの開発者が調査に使うプロキシや検査の道具が使えなくなります。得られる
  ペイロードの差は、圧縮によってほぼ消えます。
