## はじめに

メッセージ定義のスキーマと、端末を取り残さずにスキーマを変えるための互換ポリシーを定めます。定義は、
どのチャネルにも見せない施策の部分と、描画されるコンテンツの部分に分かれます。コンテンツは自由形式の
文書ではなく、レイアウト種別をタグとする直和型にします。コンテンツのオブジェクトは必ずスキーマ
バージョンを持ち、SDK は知らないバージョンに出会ったとき、推測せずにそのメッセージを飛ばします。
メジャーバージョンの内側では、スキーマは任意フィールドを増やす方向にしか変わりません。

互換ポリシーを先に述べる必要があるのは、モバイルではスキーマを取り消す手段がないからです。citywalk の
インストールベースに残る最も古い SDK は2年前のもので、それでもペイロードを取得し続けます。したがって
今日サーバが出すどのフィールドも、そのフィールドが存在する前に作られたクライアントに解釈できる形で
なければなりません。

## 動機

メッセージ定義は描画の関心ごとに見えて、実際には分散システムの関心ごとです。サーバが書き、いつ作られた
か分からない端末が読み、両側を同時に更新できる瞬間は存在しません。したがってスキーマのどの選択も、
両側があるフィールドの意味について食い違ったときに何が起きるか、という選択になります。

近道に見えるのは自由形式の文書です。管理画面が作ったものをそのまま保存して送り、SDK が認識できるものを
描画します。この近道は最初の1本を速くする代わりに、後で2回請求します。まずサーバが何も検証できなく
なります。配色の打ち間違いやボタンの文言の欠落は端末まで届いて、そこで失敗します。見えず、しかも施策が
生きているあいだには直せません。次に、どの形が正しいのかがどこにも記録されません。SDK のレンダラが
なりゆきで仕様になり、それがたまたま許容するフィールドのすべてが、誰も書き留めていない互換性の義務に
変わります。

逆の近道、つまりレイアウトごとにテーブルを切る設計は、反対側から破綻します。新しいレイアウトを1つ足す
たびに、スキーマの移行、サーバのリリース、SDK のリリースが揃うまで施策の担当者は使えません。これは
[CW-0001](../CW-0001-in-app-message-platform-scope/CW-0001-in-app-message-platform-scope-ja.md) が
脱出しようとしているリリースサイクルへ、基盤を戻す動きです。以下のスキーマは、厳格な設計から検証を、
自由形式の設計から拡張性を取ります。構造は型付きでサーバが検査し、その検査はレジストリが駆動するため、
新しいレイアウトは移行なしで追加できます。

## 詳細設計

### ユニット1：エンティティの分割

定義は5つのエンティティに分かれます。分割の線は、サーバが持つものと端末が受け取るものを分ける
[CW-0002](../CW-0002-hybrid-delivery-model/CW-0002-hybrid-delivery-model-ja.md) の境界と同じです。

- **メッセージ**：施策そのものです。名前、状態、優先度、配信期間、オーディエンスの参照、統制ポリシー、
  ホールドアウトの割合、コンバージョンイベントを持ちます。オーディエンスの参照はサーバから出ません。
- **バリアント**：描画できるコンテンツのオブジェクト1件です。実験の配分比率と言語タグを持ちます。
  バリアントが1つ、言語が1つの単純なメッセージも、バリアントをちょうど1つ持ちます。
- **トリガー**：種別、発生回数の目標、イベントプロパティに対する任意の述語式を持ちます。
- **表示条件**：遅延、画面の許可リストまたは拒否リスト、接続状態の要求を持ちます。
- **統制ポリシー**：メッセージごとの上限、表示間隔の最小値、プロジェクト全体の上限からの除外可否を
  持ちます。

バリアントをメッセージから切り出すと、A/B テストと多言語対応が2つの仕組みではなく1つの仕組みになります。
どちらも「同じ施策の、違うコンテンツ」だからです。配信サービスは端末ごとに、まず言語で、次に実験の割当で
バリアントを1つ選びます。

### ユニット2：直和型としてのコンテンツ

コンテンツは `layout` をタグとする直和型で、表示形式ごとに1つのメンバーを持ちます。中央ダイアログ、
画面端のバナー、全画面、任意の HTML、そして複数ステップの体験がメンバーです。複数ステップの各ステップは、
ダイアログまたは全画面のメンバーそのものです。各メンバーは自分のフィールドを宣言し、共通のフィールド、
すなわち見出し、本文、メディアの参照、ボタン、配色、角丸、自動クローズまでの遅延は、メンバーごとに
繰り返さず1箇所で宣言して再利用します。

ボタンは、文言と順序付きのアクションの並びで表します。アクション自体も直和型で、閉じる、外部リンクを
開く、アプリ内の遷移先へ移動する、カスタムイベントを発火する、属性を更新する、のいずれかです。ボタンの
挙動を単一のアクションではなく並びとして表すことで、1回の押下でカスタムイベントの記録と画面遷移の
両方を行えます。これはよくある要求であり、並びでなければ2つめの仕組みが必要になります。

### ユニット3：格納の表現

施策側のエンティティはリレーショナルなカラムにします。メッセージの状態、優先度、期間、ポリシーは、管理
画面と配信サービスが検索、絞り込み、結合の対象にするもので、それぞれ索引を求めます。コンテンツは
バリアントごとに1つの JSON 文書として格納します。配信サービスがコンテンツの内側を検索することはなく、
コンテンツはペイロードへ丸ごと写される不透明なデータだからです。直和型をリレーショナルに分解すると、
レイアウトごとにテーブルが増え、読み取りごとに結合が増え、得るものがありません。

この分割は場当たりの判断ではなく規則にします。何かが絞り込みや並べ替えに使うフィールドはカラムへ、
常に丸ごとしか読まれないフィールドは JSON 文書へ置きます。規則を守れば索引は意味を保ち、新しい
レイアウトはデータベースのスキーマに触れずに済みます。

### ユニット4：バージョニングと互換性

すべてのコンテンツのオブジェクトは、メジャーとマイナーからなる `schema_version` を持ちます。メジャー
バージョンの内側では、変更は追加だけです。任意フィールドの追加、アクション種別の追加、レイアウト
メンバーの追加が該当します。知らない任意フィールドに出会った SDK はそのフィールドを無視し、知らない
`layout` や知らないアクション種別に出会った SDK はメッセージ全体を飛ばします。知らないレイアウトを
半分だけ描画する状態は、何も描画しない状態より悪いからです。

メジャーバージョンの更新は破壊的変更であり、移行ではなく並行配信で扱います。移行期間のあいだサーバは
両方のバージョンを出し、端末はそれぞれの SDK が対応を宣言した最も高いバージョンを受け取ります。旧
バージョンは、稼働中の端末に占める割合が定めた閾値を下回った時点で取り下げます。端末は登録時に対応
バージョンを宣言するため、配信サービスは問い合わせずに何を出すかを決められます。

メッセージを飛ばしたことは観測できなければなりません。そうでないと、一部の利用者層を取り残した展開が、
誰も対象にならなかった施策と同じに見えます。そこで SDK は、飛ばした事実を、メッセージの識別子と非対応の
バージョンを添えた効果測定イベントとして報告します。

### ユニット5：保存時の検証

定義サービスは保存時に検証し、警告ではなく拒否します。検証の対象は、宣言されたバージョンのスキーマに
対する構造の一致、参照の整合性（参照先のセグメント、コンバージョンイベント、メディアの存在）、時刻の
整合性（開始が終了より前で、終了が未来にあること）、バリアントの配分比率の合計、コンテンツのセキュリティ
制約です。許可リストにないスキームのリンクや、実行可能なスキームを含む HTML コンテンツは拒否します。

配信時ではなく保存時に検証することが要点です。保存時の拒否は直せる人に届き、配信時の拒否は端末に届いて、
誰にも届きません。

## 検討した代替案

- **スキーマを持たない自由形式のコンテンツ文書**：採りません。サーバが何も検証できなくなるため、
  誤りは端末上で表面化します。そこでは見えず、施策の途中で直すこともできません。さらに SDK の
  レンダラが、なりゆきで文書化されていない仕様になります。
- **レイアウトごとのリレーショナルなテーブル**：採りません。新しいレイアウトのたびにデータベースの
  移行とサーバのリリースが必要になり、基盤が取り除こうとしているリリースサイクルへの結合が戻ります。
  加えて読み取りの経路に結合が増えますが、コンテンツはフィールドで検索されないため何も得られません。
- **すべてのメッセージをサーバ側で HTML として描画する**：採りません。描画の経路が1本になる点は
  確かに単純ですが、両プラットフォームのネイティブな見た目を失い、ペイロードは大幅に大きくなります。
  そして HTML を選んだ施策だけでなく、すべてのメッセージの前にコンテンツ注入の攻撃面を置くことに
  なります。
- **スキーマバージョンではなくフィールド単位で能力交渉する**：一般化しすぎであるため採りません。
  対応フィールドの集合を端末が申告する方式はバージョン番号より精密ですが、互換性の組み合わせが1次元
  から多次元になり、サーバが試験のために列挙できない組み合わせにペイロードが依存します。

## 進捗

> 開発の進行に合わせて最新の状態に保ってください。各チェックは詳細設計のユニットに対応します。

- [ ] ユニット1：5つのエンティティと、メッセージとバリアントの分割。
- [ ] ユニット2：レイアウトをタグとする直和型のコンテンツと、入れ子の直和型としてのアクション。
- [ ] ユニット3：検索対象はカラム、コンテンツはバリアントごとの JSON 文書。
- [ ] ユニット4：スキーマのバージョニング、追加だけのマイナー変更、メジャーをまたぐ並行配信。
- [ ] ユニット5：構造、参照、時刻、配分比率、コンテンツのセキュリティを対象とする保存時の検証。
